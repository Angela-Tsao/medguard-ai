MedGuard AI — Machine Learning Analysis¶

BUS AN 517 · Final project · full, reproducible analysis

MedGuard AI is a communication bridge between patients and clinicians: a patient types their medication list in their own words, and the app turns it into a standardized list with cited safety flags for a doctor or pharmacist to review. It is decision support for clinicians, not a tool for patients to make medication decisions.

This notebook covers the machine-learning part: finding medication names in messy free text. It runs every step in order:

Section What it does
1 Problem framing: what is predicted and which error is costly
2 Data: generate the synthetic sentences, split them without leakage
3 Features
4 Train 7 methods (2 baselines + 5 models)
5 Choose each threshold by cost on the validation set
6 Compare methods on the held-out test sets (with 95% bootstrap CIs)
7 What the model learned (feature importance) and speed
8 End-to-end check: do the right safety alerts appear?
9 Six stress tests with messy, realistic text (scored once with the frozen model)
10 Error analysis, conclusions and limitations

How to run: open this notebook in the medguard folder (or upload the folder to Colab), then Run all (about 3 minutes).

Reproducibility. By default the notebook uses the frozen, saved models in models/, the exact models behind every number in our report, so Run all reproduces those numbers exactly. Set RETRAIN = True below to regenerate the data and retrain all seven methods from scratch (about 5 more minutes). The data comes back identical, and logistic regression gives the same results within one word per test set; random forest, gradient boosting and spaCy can shift slightly because multithreaded training is not bit-for-bit repeatable. The source code for each step is in src/.

1. Problem framing¶

Task. For every word (token) in a sentence, predict: is this word a medication name? (binary classification). A detected word is then matched to one standard drug name in our dictionary (101 drugs, 200 names: generics and brands).

Why ML and not a dictionary lookup? People do not write names the way a dictionary does: typos (metforman), OCR noise from bottle photos (L1SINOPR1L), brand names, abbreviations, doses glued to names (lisinopril10mg). An exact lookup misses these. A fuzzy (similarity) match finds them but also flags many everyday words. The model combines similarity with other evidence.

Which error is costly? In a safety tool, a missed medication can hide a dangerous interaction, while a false flag only costs the user one click to remove. We therefore set every threshold by minimizing

$$\text{cost} = 10 \times \text{missed medications} + 1 \times \text{false flags}$$

on the validation set (Week 3: asymmetric error costs). Test sets are never used to choose anything.

2. Data¶

No public dataset has messy, patient-written medication lists with word-level labels, so we generate labeled sentences (src/gen_data.py) from 60 sentence templates, 101 drugs and a 6,000-word everyday vocabulary, in five input styles: clean, misspelled, OCR noise, brand names, and dose attached.

Leakage control. A model can look good just by memorizing drugs or sentence patterns it has seen. So the split is done three ways at once: by drug (a test drug never appears in training), by template and by everyday word.

3. Features¶

Each word is described by two groups of features (src/medguard.py):

  1. Hand-made features: similarity to the closest dictionary name (rapidfuzz, with OCR-aware variants such as 1→l, 0→o), whether it is an exact dictionary name, length, digits, capital letters, cue words nearby (take, mg, pill), drug-like suffixes (-pril, -olol, -statin).
  2. Character n-grams (2–4 letters, TF-IDF): lets the model learn what drug names "look like" even when misspelled.

The context model also adds the previous and next words.

5. Threshold choice (validation set only)¶

For each model we try every threshold and keep the one with the lowest cost (10 × missed + 1 × false flag) on validation. Because a miss costs 10 times more, the chosen threshold leans toward flagging more words, and the doubtful ones are sent to the user to confirm.

Reading the results. Exact match only works on clean names. Fuzzy match finds most misspellings but flags many everyday words (low precision). 9. Stress tests with messy, realistic text¶

After the main evaluation, we scored six additional test sets once each, with the frozen model and thresholds (nothing was tuned on them). Every medication mention was labeled by hand by one team member (data/sealed_test_*_gold.py, *_labels.py).

Test What it contains Source
1 150 sentences, correct spelling team-written (generated with AI)
2 Test 1 rewritten with typos and doses AI rewrite of test 1
3 500 sentences, 50 phrases × 10, sound-alike spelling, many rare drugs AI-generated
4 500 sentences, 125 drugs × 4 spellings (incl. names split by a space) provided by outside contributors; shows signs of AI generation
5 200 sentences, one drug each, often written two ways provided by outside contributors; shows signs of AI generation
6 200 everyday mentions (notes, refills, nurse charting, short forms) most realistic; source to be confirmed

Two numbers are reported for each test:

  • Known drugs found and mapped correctly: model ability on the 101 drugs we cover (fair comparison between methods).
  • All drugs found and mapped correctly: product reality, counting medications that are not in our list.

Tests 1–3 have one word per medication and use src/eval_sealed.py; tests 4–6 can split a name over several words (metop ro-lol) or hold several drugs per sentence, so they use mention-level scoring in src/eval_mentions.py (a mention counts as found if any of its words is detected and mapped to the right drug).

9b. Clinical scenario tests (what the app must show)¶

The tests above measure the model (does it find the names?). They cannot catch a missing rule or a medication that disappears: the "correct" alerts are produced by the same rule set, so if a rule is missing, the answer key is missing it too. A teammate found four such problems by typing realistic cases into the live app (two blood thinners together, Toradol, Tylenol PM, tramadol + sertraline). We turned them, and similar cases, into fixed scenario tests that every new version must pass (data/scenario_tests.csv, src/eval_scenarios.py).

Conclusions¶

  1. The model is better than the baselines. It finds as many medications as fuzzy matching, but with much higher precision, so the patient and clinician see far fewer false flags. Exact lookup fails on any misspelling.
  2. The threshold is set by cost, with a missed medication counted as 10 false flags, on validation data only.
  3. Where it fails:
    • short forms people really use (ibu, atorva, hctz, doxy, amio): too different from the full name;
    • names split by a space (metop ro-lol): the model reads one word at a time;
    • look-alike names mapped to the wrong drug (hydrocortisone → hydrocodone, azilsartan → valsartan);
    • medications outside our 101-drug list, about half of real mentions.
  4. Guardrails that address these failures: every match is confirmed by the user; weak matches and everyday words are never auto-mapped; the clinician sees the patient's original text with recognized names highlighted, so unrecognized medications are not lost; every flag is labeled for doctor or pharmacist review.

Limitations and next steps¶

  • Gold labels were made by one person; a second person should spot-check them.
  • Several stress tests appear to be AI-generated; a set of genuinely patient-written lists is still needed.
  • Next: add common short forms and the RxNorm name list (largest gain), join neighboring word fragments before matching, and use a stricter cut-off for auto-mapping look-alike names, all tuned on validation data, then tested on a new unseen set.
